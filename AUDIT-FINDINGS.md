# Pre-Delivery Audit — High-Risk Modules

Generated by an automated multi-agent review (12 high-risk clusters; every finding adversarially verified). **79 confirmed findings**: 4 critical, 34 high, 31 medium, 10 low.


## CRITICAL (4)

### C1. Invoice payment synced with empty invoice reference after first-time invoice sync
- **Location:** `lib/accounting/sync-service.ts:378` — _accounting-sync / correctness_
- **Issue:** When the invoice is not yet synced, the code calls syncInvoice() and re-fetches the external id into `reSync` (validated on lines 364-375). But line 378 then computes `invoiceExternalId = invoiceSync?.external_id || ''` using the ORIGINAL `invoiceSync` result, which was null in this branch. So `reSync` is discarded and `invoiceExternalId` becomes ''. The payment payload (line 379) then carries no invoice link. In QuickBooks createPayment(), an empty `invoice_external_id` falls through to the bill branch / 'must reference invoice or bill' error; in Xero it posts a payment with `InvoiceID: ''`. Result: payments silently detach from their invoice or fail, corrupting AR balances on the very first payment for any invoice.
- **Fix:** After the re-sync block, use the freshly fetched id: `const invoiceExternalId = invoiceSync?.external_id || reSync?.external_id || ''` (hoist `reSync` out of the if-block scope), and throw if it is still empty before building the payload.

### C2. Bulk rate import endpoint is unauthenticated and bypasses RLS
- **Location:** `app/api/rates/bulk/import/route.ts:17` — _b2b-pricing / security_
- **Issue:** POST /api/rates/bulk/import performs no session/user/role check and no shared-secret/HMAC verification, yet it uses createServerClient() (the Supabase service-role key, which bypasses Row-Level Security). middleware.ts deliberately lets all /api/* through, so any anonymous internet caller can insert/update arbitrary rows into all 14 rate tables (accommodation_rates, transportation_rates, nile_cruises, fixed_costs, etc.). An attacker can overwrite supplier costs and rates that feed every quote, directly corrupting all downstream pricing, or use it as a data-exfiltration/poisoning vector.
- **Fix:** Add an auth gate at the top of POST: verify an authenticated admin/ops session (cookie-based Supabase user + role check) or require a shared secret (e.g. INTERNAL_API_SECRET) / HMAC. Reject with 401 before touching the DB. Apply the same gate to the export route.

### C3. Commission generation queries a non-existent table (itinerary_day_services)
- **Location:** `app/api/itineraries/[id]/generate-commissions/route.ts:40` — _expenses-commissions / correctness_
- **Issue:** The route SELECTs from 'itinerary_day_services' (line 40) and later UPDATEs 'itinerary_day_services' (line 129). That table does not exist in this codebase: the real services table is 'itinerary_services' (used in 31 places, defined in migrations 20260220_add_service_versions.sql / 20260226_multi_currency_services.sql, and used by the parallel working route app/api/itineraries/[id]/days/[dayId]/services/route.ts). The Supabase select against a missing table errors, so the route always returns 500 'Failed to fetch services' (or, if it silently returns no rows, 'No new commissions to generate'). Net effect: this endpoint NEVER generates a single commission and silently does nothing — a core feature of the module is completely broken pre-delivery.
- **Fix:** Replace both 'itinerary_day_services' references with 'itinerary_services' (line 40 SELECT .from('itinerary_day_services') -> .from('itinerary_services'); line 129 UPDATE likewise). Confirm the join filter .in('day_id', dayIds) matches the itinerary_services.day_id column (it does, per app/api/clients/[id]/route.ts:175).

### C4. Unauthenticated, RLS-bypassing write endpoint (create/update/delete itineraries)
- **Location:** `app/api/pricing-grid/save/route.ts:45` — _pricing-grid / security_
- **Issue:** POST /api/pricing-grid/save has no caller verification (no session/user check, no shared secret, no HMAC). middleware.ts explicitly lets all /api/* through ('they handle their own auth'), and this route uses createServerClient() = the SUPABASE_SERVICE_ROLE_KEY, which BYPASSES Row-Level Security. Any anonymous internet caller can therefore create itineraries, and via config.itineraryId update/overwrite ANY existing itinerary in the database (lines 94-104) and cascade-delete its days and services (lines 133-153) — there is no ownership/tenant check that itineraryId belongs to the caller (IDOR). This is a full unauthenticated write/delete primitive over the itineraries dataset.
- **Fix:** Add an auth check at the top of POST: resolve the Supabase user session from cookies (createServerClient with cookie adapter) and reject with 401 if no user, OR require a shared INTERNAL_API_SECRET header. Then verify the authenticated user/org owns config.itineraryId before update/delete (scope the .eq('id', ...) by owner_id/org_id, or re-check via an RLS-respecting client).


## HIGH (34)

### H1. OAuth callback has no CSRF state validation (login/account CSRF)
- **Location:** `app/api/auth/accounting/callback/route.ts:35` — _accounting-auth-reports / security_
- **Issue:** The OAuth `state` is built in connect/route.ts as the plain string `${userId}:${provider}` with no random, unguessable nonce, and the callback only splits it into userId/provider — it never compares it against a value stored server-side or in a signed cookie before the redirect. Both providers (xero-provider.ts getAuthUrl, quickbooks-provider.ts getAuthUrl) pass this predictable state straight through. Because state is fully predictable and unverified, an attacker can forge a callback URL (or replay/swap a valid `code`) that binds the attacker's accounting tenant to a victim's userId, or trick a victim into connecting the attacker's books. The callback then upserts those tokens against the supplied userId using the service-role client (line 54-69), so the victim's financial sync is silently pointed at attacker-controlled data. This is the classic OAuth login/account-linking CSRF.
- **Fix:** Generate a cryptographically random nonce per connect request, store it server-side (e.g. an HttpOnly cookie or a short-lived DB row keyed to the session user), and embed it in state alongside the provider. In the callback, look up the stored nonce, verify it matches, confirm it maps to the currently authenticated session user, then delete it (single-use). Reject the callback if validation fails instead of upserting.

### H2. Disconnect trusts client-supplied userId — IDOR via service-role client
- **Location:** `app/api/auth/accounting/disconnect/route.ts:11` — _accounting-auth-reports / security_
- **Issue:** The route reads `userId` from the request JSON body and deletes accounting_tokens with `.eq('user_id', userId)` using the SUPABASE_SERVICE_ROLE_KEY client (line 4-7), which bypasses RLS. middleware.ts does not authenticate /api/* routes, and there is no session/user check here. Any unauthenticated caller can POST `{ userId: '<any user>', provider: 'xero' }` and delete another tenant's accounting connection, breaking their sync and forcing a re-auth. The same trust-the-body pattern in connect/route.ts and callback/route.ts means the entire connection lifecycle is keyed off an unverified client-supplied user id.
- **Fix:** Derive the user from the authenticated session server-side (createServerClient with the request's auth cookie / supabase.auth.getUser()) instead of from the request body, and only delete tokens for that authenticated user. Reject the request with 401 if there is no valid session. Apply the same session-derived userId in connect/route.ts and the callback.

### H3. Summary aggregates revenue/cost across mixed currencies without conversion
- **Location:** `app/api/profit-loss/route.ts:157` — _accounting-auth-reports / correctness_
- **Issue:** Each itinerary carries its own `currency` (line 139, defaulting to 'EUR'), but the summary sums total_revenue, supplier_cost, and manual_expenses across all itineraries directly (lines 157-161) with no currency normalization. A trip priced in EGP (~56 to 1 EUR) is added to EUR trips as if 1 EGP = 1 EUR, so total_revenue, total_expenses, total_profit, and average_margin are meaningless whenever more than one currency is present. Given the app supports USD/EUR/GBP/EGP, multi-currency data is expected and the headline P&L numbers will be badly wrong.
- **Fix:** Convert each trip's revenue and costs to a single reporting currency before summing (use convertCurrency from lib/currency-service with fetched rates, ideally the historical rate captured at booking via getHistoricalRate), or group the summary per-currency. At minimum, document/return a `currency` on the summary and refuse to add differing currencies.

### H4. Financial reports endpoint is unauthenticated and exposes all tenants' financials
- **Location:** `app/api/financial-reports/route.ts:49` — _accounting-auth-reports / security_
- **Issue:** GET reads invoices, expenses, and itineraries via the service-role client (line 4-7, bypassing RLS) with no session/auth/secret check. Per the project's auth model, middleware.ts lets all /api/* through expecting per-route auth, and there is none here. Any unauthenticated caller can hit /api/financial-reports (and the equally open /api/profit-loss) and read full revenue, expenses, supplier costs, margins, client names, and commission recipients across the entire business. This is a direct confidential-data exposure, not just a missing nicety.
- **Fix:** Add an authentication check at the top of the handler: resolve the session user via a cookie-bound Supabase server client (supabase.auth.getUser()) and return 401 if absent, and enforce role/tenant scoping. Apply the same guard to profit-loss/route.ts. If these are meant to be internal, require the INTERNAL_API_SECRET shared-secret header.

### H5. Expense payment synced with empty bill reference; missing re-fetch and no failure guard
- **Location:** `lib/accounting/sync-service.ts:435` — _accounting-sync / correctness_
- **Issue:** When the bill is not yet synced, line 432 calls syncExpense(expenseId) but the code never re-fetches the new external id. Line 435 uses `billSync?.external_id || ''`, which is still null/'' from the pre-sync query (line 422-429). The bill payment is therefore created with `bill_external_id: ''`. In QuickBooks createPayment this throws 'Payment must reference an invoice or bill'; in Xero it posts a payment with `InvoiceID: ''`. Unlike syncInvoicePayment there is not even a guard that the bill sync succeeded. AP payments will fail or detach on first sync of any expense.
- **Fix:** After calling syncExpense, re-query accounting_sync_log for the expense's external_id, throw an AccountingSyncError if still missing, and use that value for billExternalId.

### H6. Retry query never picks up newly failed entries (NULL next_retry_at excluded)
- **Location:** `lib/accounting/sync-service.ts:467` — _accounting-sync / correctness_
- **Issue:** syncInvoice/syncExpense/syncInvoicePayment/syncExpensePayment write `sync_status='failed'` on error but never set `next_retry_at`, so it stays NULL. retrySyncErrors filters with `.lte('next_retry_at', now)`. In Postgres, a NULL value is never `<=` anything, so every first-time failure (next_retry_at IS NULL) is permanently excluded from the retry batch. Only entries that have already been retried once (and thus had next_retry_at set in the catch on line 505) are ever eligible — but they can only get there by being selected, which they never are. Net effect: the entire retry mechanism processes nothing, so transient failures are never retried.
- **Fix:** Set `next_retry_at` to now() (or a short delay) in each function's failure upsert, OR change the filter to include NULLs, e.g. `.or('next_retry_at.is.null,next_retry_at.lte.' + new Date().toISOString())`.

### H7. Payments are not idempotent — retries double-create payments in the accounting system
- **Location:** `lib/accounting/sync-service.ts:380` — _accounting-sync / correctness_
- **Issue:** syncInvoicePayment (line 380) and syncExpensePayment (line 437) unconditionally call provider.createPayment() with no check of accounting_sync_log for an existing synced payment, unlike syncInvoice/syncExpense which check existingSync and call update vs create. If a payment's API call succeeds at the provider but the subsequent upsertSyncLog write fails (or the route is re-invoked, or retrySyncErrors re-runs it), a second payment is created in QuickBooks/Xero for the same internal payment. This double-applies cash against the invoice/bill and overstates received/paid amounts — a money-integrity defect.
- **Fix:** Before createPayment, query accounting_sync_log for (provider, entity_type, entity_id) with sync_status='synced'; if an external_id already exists, return without re-creating. Also pass the provider an idempotency key (QB supports a RequestId; use the internalId).

### H9. Tax dropped when mapping invoices/bills to QuickBooks and Xero — synced totals mismatch source
- **Location:** `lib/accounting/quickbooks-provider.ts:285` — _accounting-sync / correctness_
- **Issue:** mapInvoiceToPayload populates tax_rate/tax_amount/subtotal, but mapToQBInvoice (QB) and mapToXeroInvoice (Xero) never emit any tax fields (no TxnTaxDetail/TaxType/TaxAmount). Xero's mapper sets LineAmountTypes:'Exclusive' and provides no per-line tax, so Xero will not add the tax the source invoice has. ### H10. Cabin allocation silently drops to €0 when single/double/triple rate is missing for an odd or unsplittable pax count
- **Location:** `lib/ai/cruise-pricing.ts:113` — _ai-itinerary / correctness_
- **Issue:** calculateCabinAllocations only builds combinations from double/triple/single, and each cabin type is only added when its rate is > 0 (lines 103, 108, 113). The allocation is kept only if allocatedPax === totalPax (line 121). So if a leftover passenger can only fit in a cabin whose rate is 0 (e.g. 3 pax where rate.single = 0 and rate.triple = 0, or 1 pax where rate.single = 0 — single rates are commonly left unconfigured), NO allocation sums to totalPax and the function returns []. getCruiseRate then returns noRate with found=false (line 213), so the ENTIRE cruise accommodation is priced at €0 across all nights. The only signal is a console warning; the quote total is silently understated (the agency eats the whole cabin cost). A rate of 0 for one cabin type should not nullify all pricing.
- **Fix:** Treat a 0 rate as 'cabin type unavailable for allocation' but still surface a hard failure/warning when no allocation covers all pax. At minimum, in getCruiseRate, when allocations.length === 0 AND totalPax > 0, push an explicit warning into the returned object (and into the route's generation_warnings) instead of silently returning found=false with €0; ideally fall back to pricing the odd passenger at the double pp rate (single-supplement model) so the cabin is never free.

### H14. OAuth state is the raw user_id with no signing/CSRF binding — Gmail tokens written to an attacker-chosen user_id
- **Location:** `app/api/auth/google/callback/route.ts:59` — _auth-core / security_
- **Issue:** The callback reads `state` straight from the query string (line 17) and uses it verbatim as `user_id` when upserting into `gmail_tokens` (line 59), with onConflict 'user_id'. The state is generated in app/api/gmail/connect/route.ts as `getAuthUrl(userId)` where userId comes from the POST body with no session check, so state is an unsigned, caller-supplied value. Two concrete attacks: (1) Login-CSRF / token implantation — an attacker completes Google consent with their own account but a state equal to the VICTIM's user_id, causing the victim's record to be overwritten so the victim's app reads/sends mail through the attacker's mailbox (or vice-versa). (2) Because the upsert overwrites by user_id, anyone who can trigger the callback with a known user_id can clobber that user's stored refresh_token. There is no verification that the Google account email matches the user, no per-session nonce, and no signature on state.
- **Fix:** Generate state as a signed, single-use, session-bound nonce (HMAC of a random value + the authenticated user id, stored server-side or in a signed httpOnly cookie). In the callback, verify the nonce/signature and resolve user_id from the verified session — never trust user_id from the URL. Reject if the bound user does not match the logged-in session.

### H17. Upsert mis-handles duplicate unique keys within the same import batch
- **Location:** `app/api/rates/bulk/import/route.ts:149` — _b2b-pricing / correctness_
- **Issue:** Existence is checked once per 50-row batch against the DB (existingKeys). Two CSV rows sharing the same service_code/cruise_code/cost_type that does NOT yet exist both fail the existingKeys.has() check and are both pushed to toInsert, then inserted together via a single .insert([...]). If the table has a unique constraint on the key, the whole insert errors and the entire batch's new rows are lost; if it doesn't, two conflicting rows are created. Either way the import is not idempotent and silently corrupts/loses data for duplicate keys.
- **Fix:** De-duplicate rows by uniqueKeyColumn before splitting (keep last occurrence), and/or replace the manual exists-check + insert/update split with a single supabase.upsert(batch, { onConflict: uniqueKeyColumn }) so duplicates within and across batches resolve deterministically.

### H21. Deleting a payment force-resets invoice status to 'sent', clobbering draft/cancelled/overdue
- **Location:** `app/api/invoices/[id]/payments/[paymentId]/route.ts:55` — _invoices / correctness_
- **Issue:** After deleting a payment the route recomputes status as only one of 'paid' | 'partial' | 'sent'. The `else` (totalPaid === 0) branch hard-codes status='sent'. If the invoice was 'draft' (never issued), 'cancelled', or 'overdue', removing its last payment silently flips it to 'sent'. A cancelled invoice becomes active again; a draft becomes 'sent' without ever being sent. This corrupts invoice state and can re-expose cancelled invoices to the reminder engine (reminders/route.ts only excludes 'paid','cancelled').
- **Fix:** Preserve the existing status when totalPaid === 0 by selecting the current `status` alongside `total_amount` and only downgrading from 'paid'/'partial'. E.g. fetch current status; if totalPaid===0 keep the prior non-payment status (or 'sent' only if it was previously 'partial'/'paid'); never overwrite 'draft'/'cancelled'/'overdue'.

### H22. PUT lets caller overwrite payment-derived fields (amount_paid, balance_due, status, paid_at)

When total_amount changes, recompute balance_due AND derive status consistently (paid/partial/sent) from amount_paid, mirroring the payment-delete logic.

FOR UPDATE locks the bookings row before summing booking_payments, or compute totals in SQL (sum aggregate) atomically. At minimum serialize per booking_id. Also add an idempotency key / unique constraint (transaction_reference) to reject accidental duplicate submissions.
